# BDD with Gherkin

How behavior-driven scenarios fit into this framework next to the plain Playwright specs. Built in milestone M7 with [`playwright-bdd`](https://github.com/vitalets/playwright-bdd); see [ROADMAP.md](ROADMAP.md) for progress.

## How it works

```
features/login.feature        (Gherkin, written from a user story)
        │
        ▼  npx bddgen         (a generation step, runs before the tests)
.features-gen/login.feature.spec.js   (an ordinary Playwright test file, generated)
        │
        ▼  npx playwright test
runs next to tests/ui/..., tests/api/...   (your normal specs)
```

- `bddgen` turns each scenario into a normal Playwright test. For Playwright a scenario is just another test: same workers, retries, traces, HTML and Allure reports.
- Step definitions (`Given I am on the login page`) call the existing page objects and fixtures (`loginPage`, `homePage`, accounts from `src/config/accounts.ts`). No second framework and no duplicated locators.
- Tags on scenarios (`@smoke`, `@readonly`, `@regression`) work like tags on specs, so `TEST_ENV=uat` also runs only the read-only scenarios, and `npm run check:tags` covers them.
- The scenarios get their own Playwright project, so they can run alone (`--project=bdd`) or together with everything else.
- `.features-gen/` is generated output: it is git-ignored and recreated before every run.

In Java terms: Cucumber-JVM and TestNG in the same Maven project, sharing the same page objects. Here the shared layer is the fixtures.

## In this repo

```
features/login.feature        Gherkin: Background, Scenarios, a Scenario Outline with Examples
src/bdd/fixtures.ts           mergeTests(bddTest, appTest) and createBdd(): Given / When / Then
src/bdd/steps/*.steps.ts      step definitions, receiving page objects and API clients by name
.features-gen/                generated by npx bddgen (git-ignored, never edited)
```

- `src/bdd/fixtures.ts` combines two test objects with `mergeTests`: `playwright-bdd`'s own (the machinery that matches sentences to steps and records them in the report; `createBdd` refuses a test without it) and ours from `src/fixtures/hybrid.ts` (page objects and API clients). A scenario runs with one test object, so it needs both in one.
- The `bdd` project in `playwright.config.ts` points at `.features-gen/` through `defineBddConfig`. A step without a definition fails during generation, not halfway through a run.
- Tags: features carry `@bdd` and `@regression`, scenarios that cannot change shared data `@readonly`. While the plain login and search specs still exist, scenarios are not tagged `@smoke`, so smoke does not test the same behavior twice.
- `features/login.feature` is the BDD version of `tests/ui/guest/login.spec.ts`; both are kept side by side for comparison.

## Commands

```bash
npx bddgen                          # generate .features-gen/ (fails if a step has no definition)
npm run test:bdd                    # only the scenarios
npm test                            # everything: plain specs and scenarios
TEST_ENV=uat npm run test:bdd       # read-only scenarios on UAT
npx playwright test --grep @bdd     # scenarios by tag (after npx bddgen)
```

`npm test`, `npm run test:smoke`, `npm run test:bdd` and `npm run check:tags` run `bddgen` first, so generated tests always match the feature files.

## Plain specs or BDD scenarios?

Both stay in the repo. The rule is to never test the same thing twice: duplicated coverage means double maintenance and double failures.

| Use BDD scenarios for                                                                                         | Keep plain specs for                                            |
| ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| business flows a product owner or business analyst should read and agree on (login, search, checkout journey) | API and contract tests (zod schemas, negative datasets)         |
| acceptance criteria from user stories (Given, When, Then)                                                     | data-driven tables with many rows (payment methods, NEG-01..32) |
| living documentation of the shop's behavior                                                                   | mocked states, visual snapshots, email polling                  |
|                                                                                                               | technical edge cases nobody outside QA needs to read            |

When a scenario covers something an existing spec already tests, decide case by case: replace the spec, or keep the spec for the technical details and let the scenario describe the business behavior.
